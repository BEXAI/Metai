# T9 — spectator-web-engineer

Owns: `web/` only. Static, no-build SPA served by Workers Assets at `/watch`
(spec §architecture.spectator_web), plus the offline verifier bundled for the
browser. No new dependencies; no server code; consumes only the public HTTP
API and the compiled kernel verifier.

Tests: `npx vitest run --config web/vitest.config.ts` — 12/12 green (see
"Test wiring" below for why a second config file exists). Typecheck: `web/`
is excluded from the root `tsconfig.json` (pre-existing, not something I
changed), so `npx tsc --noEmit` has nothing to check there; the two TS files
I added (`web/verify-entry.ts`, `web/partial-verify-entry.ts`) are validated
by actually bundling them with esbuild in `web/build.sh` instead — that's the
practical equivalent of a type-check for files outside the checked tree, and
`web/build.sh` currently bundles both cleanly (see "Verifier build" below).
No seed draws: T9 has no randomness and touches no `SeedStream`.

## Mount point: `/watch` (important cross-track fact)

Spec puts the SPA at `/watch`. `src/index.ts` (T7) forwards matching requests
with `env.ASSETS.fetch(request)` using the **unmodified** request (path still
`/watch/...`), and `wrangler.jsonc`'s `assets.directory` is `web/public` (already
correct, untouched). That only works if the served files physically live
under `web/public/watch/` — so that's where everything is:
`web/public/watch/index.html`, `web/public/watch/js/**`,
`web/public/watch/css/styles.css`, `web/public/watch/verifier.js`,
`web/public/watch/verify-entry.js`. All root-absolute references inside the
app use the `/watch/...` prefix accordingly (`index.html`'s stylesheet/script
tags, and the dynamic `import('/watch/verify-entry.js')` in `replay.js`).
Hash-routing means the browser only ever requests the one path
(`/watch` or `/watch/`); everything else is client-side, so this is the only
place the prefix matters. If Cloudflare's asset serving turns out not to
auto-redirect bare `/watch` → `/watch/` in practice, that's a T7-side fix
(rewrite the path before calling `ASSETS.fetch`, or set `html_handling` in
`wrangler.jsonc`) — flagging it here since I can't touch either file.

## What's built

- `web/public/watch/index.html` — strict CSP meta (`default-src 'self'` etc,
  no `unsafe-inline`/`unsafe-eval`), no inline script/style, static nav to the
  three parameterless pages, footer stating a window asking for a key is
  hostile (word-for-word per spec), loads `js/main.js` as a module.
- `web/public/watch/css/styles.css` — the one stylesheet; all board/theme
  colors, layout, dark/light via `prefers-color-scheme` + `data-theme`
  override.
- `web/public/watch/js/dom.js` — the ONLY file that calls
  `createElement`/`createElementNS`; every other file goes through it.
  `innerHTML` (or any raw-markup API) appears nowhere in `web/public/js` —
  enforced by `web/tests/static-checks.test.ts`.
- `web/public/watch/js/api.js` — fetch helpers + envelope unwrapping (see
  "API shapes" below) + `subscribeGameEvents` (SSE with polling fallback,
  emits normalized `{seq,type,data,at}` events either way).
- `web/public/watch/js/router.js` — tiny hash router; each page module
  exports `mount(container, params, query) -> { dispose() }`.
- `web/public/watch/js/shapes.js` — small accessors over the *real* API/event
  shapes (see below); a couple of spots stay alias-tolerant where a game's
  exact key name could still reasonably vary (chinese_checkers/backgammon
  point-list keys).
- `web/public/watch/js/pages/{live,game,replay,agents,leaderboards,docket}.js`
  — the six pages from spec §spectator.pages.
- `web/public/watch/js/boards/*.js` — one renderer per board family
  (`grid.js` for chess/checkers/reversi/connect_drop/tictactoe, `go.js`,
  `hex.js`, `morris.js`, `chinese_checkers.js`, `backgammon.js`,
  `landlord.js` + `islanders.js` behind `schematic.js`), dispatched by
  `boards/index.js`. Every renderer falls back to `view.board_text` or a raw
  JSON `<pre>` when it doesn't recognize the shape (`boards/common.js
  #renderFallback`).
- `web/build.sh` + `web/verify-entry.ts` + `web/partial-verify-entry.ts` —
  the browser verifier (see below).
- `web/tests/static-checks.test.ts` + `web/vitest.config.ts` — see "Test
  wiring".

## Board renderer data shapes (read from the actual landed game code, not
guessed — `src/games/<id>/rules.ts` + `index.ts` as of this writing)

Every renderer takes the PUBLIC view (`event.data.public` live, or
`replay.initial_state` on the replay page — the latter is the raw internal
state, which for every M1/M2 game turns out to be byte-identical in the
fields the renderer reads, since each publicView is a near-passthrough of
those specific fields; chess is the one exception, handled below).

- **chess**: NO board field in `publicView` — only `fen` (computed). The raw
  state has `board: string` (64 chars, FEN square order, index=rank*8+file,
  rank0=rank8/top). `grid.js#normalizeChess` accepts EITHER `view.fen`
  (parses the FEN board field) OR `view.board` (raw layout), so both the live
  page and the replay page's initial-position render work.
- **tictactoe**: `board`: 9-char string over `.XO`; index=(row-1)*3+col, row
  counted 1..3 from the BOTTOM.
- **connect_drop**: NO `board` key — `cols`: array of 7 strings over `XO`,
  each column bottom-to-top.
- **reversi**: `board`: 64-char string over `.BW`; index=(row-1)*8+col, row
  1..8 from the TOP (a1 = top-left, standard Othello orientation).
- **checkers**: `board`: string of N²/2 chars, ONE PER DARK SQUARE, numbered
  1.. (32 for 8x8 english, 50 for 10x10 international); row 0 = top; square 1
  sits at (row 0, col 1); `.`/`b`/`w` (men) / `B`/`W` (kings).
  `grid.js#normalizeCheckers` derives (row,col) from the square number and
  labels each dark cell with its square number (no file/rank axis — matches
  the game's own square-number notation).
- **hex**: `size`, `board`: size² chars row-major from row 1 = the TOP (no
  flipping needed, unlike Go); `.`/`X`(p0)/`O`(p1).
- **nine_mens_morris**: `board`: 24-char string in POINTS order, EXACTLY
  `['a1','a4','a7','b2','b4','b6','c3','c4','c5','d1','d2','d3','d5','d6',
  'd7','e3','e4','e5','f2','f4','f6','g1','g4','g7']` (matches
  `src/games/nine_mens_morris/rules.ts#POINTS` — verified, not assumed).
- **go**: `size`, `board`: size² chars row-major, index=row*size+col, row 0 =
  the BOTTOM (opposite of hex!). Column letters skip `I`, shown on both top
  and bottom edges per the spec's own trap note.
- **backgammon**: `points`: 24-entry array, index=point-1, SIGNED integer
  counts (positive=p0, negative=p1); `bar`/`off`: `[p0Count, p1Count]`. Lines
  up with `boards/backgammon.js` unchanged from the first draft — this one I
  got right by inference before the game landed, and confirmed after.
- **chinese_checkers**: `board`: 121-char string, `.`/`0`..`5` (seat digit),
  in the EXACT doubled-coordinate order generated by
  `src/games/chinese_checkers/rules.ts#HOLES` (rows 1..17 top-to-bottom,
  `ROW_COUNTS = [1,2,3,4,13,12,11,10,9,10,11,12,13,4,3,2,1]`, columns centered
  on 13 stepping by 2). `boards/chinese_checkers.js` reproduces that exact
  generation loop so `view.board[i]` lines up with hole `i`, then converts
  doubled (c,r) → pixel via `x=c*(U/2), y=r*(U*sqrt(3)/2)` (equilateral
  triangular lattice — the geometry this doubled-coordinate scheme
  represents).
- **landlord**: `props`: `{[propId]: {owner, houses, mortgaged}}` (keyed by
  id, e.g. `'cinder'`), `pos`: `{[playerId]: spaceIdx 0..39}`. There is NO
  space-name/position table in the public view (only property ids), so
  `boards/landlord.js` hardcodes the 40-space layout (name/kind/group per
  space) copied from `src/games/landlord/board.ts`'s `BOARD`/`STREETS`/
  `TRANSITS`/`UTILITIES` tables — this is static public board metadata (names
  and positions aren't secret; only deck order is), not rules logic, so
  duplicating it for display is in-bounds for a read-only renderer.
- **islanders**: `terrain`/`tokens`: `Record<hexLetter, ...>` (A-S, 19 land
  hexes); `villages`/`cities`/`roads`: `Record<vertexOrEdgeId, PlayerId>`
  (vertex ids are 3 sorted hex letters, edge ids are 2); `raider`: hex letter.
  `boards/islanders.js` reproduces
  `src/games/islanders/rules.ts#buildGeometry`'s exact axial-coordinate
  generation for the 19 land + 18 sea hexes, then derives a vertex's pixel
  position as the centroid of its 3 hex centers and an edge's segment as the
  midpoint between its 2 hex centers, perpendicular, one hex side-length long
  (both exact for a regular hex grid, not an approximation).
- Both landlord and islanders also always render `board_text` alongside the
  schematic (spec explicitly allows board_text-first as an acceptable v1 for
  these two).

All of the above was verified with a headless smoke test (a ~40-line DOM
stub + realistic sample states per game, not part of the deliverable — see
"Verification performed" below) rather than just asserted from reading code.

## API shapes actually returned (src/api/handlers.ts, src/api/http.ts, T7)

Every enveloped response is `{ ok: true, data, metadata }` or
`{ ok: false, error: {code,message}, metadata, data? }` — **except** the live
`GET /api/games/:id/events` proxy, which forwards the Durable Object room's
raw `{ events, latest_seq }` response unmodified (no envelope) when the game
is live; the D1 fallback path (ended games, or room unavailable) IS enveloped
and nests each event one level deeper: `{ seq, event: {type,data,at?},
created_at }`. `api.js#getJson` unwraps the envelope when present and returns
the raw body otherwise; `api.js#normalizeEvent` collapses both event shapes
to `{seq,type,data,at}` so callers never see the difference.

Per-endpoint `data` shape actually returned (confirmed by reading the handler
bodies, not the spec prose, which doesn't go this deep):
- `GET /api/games` → `{ games: [...] }`, each row `{id, game, variant,
  division, season_id, status, commitment, drand_round, reveal_secret (null
  until ended), seats, ruleset_version, started_at, ended_at, result,
  replay}`. **No live board/turn/deadline field at all.**
- `GET /api/games/:id` → `{ game: <same row shape> }`.
- `GET /api/games/:id/events` → see above; each `move`/`timeout`/`start`
  event's `data` carries `{turn_index, player, agent_id, notation,
  state_hash, public: game.publicView(state), board_text, commentary?,
  forced?}` (src/rooms/core.ts) — **this is the only place the live board
  exists.** Event types (notes/T6.md): `start, move, timeout, strike,
  draw_offer, draw_accept, resign, forfeit, end, reveal`.
- `GET /api/games/:id/replay` → `{ replay: <ReplayFile> }` (frozen shape,
  `src/kernel/replay.ts` — used as-is).
- `GET /api/agents/:handle` → `{ agent, homologations, ratings, record:
  {wins,losses,draws,sample} }`.
- `GET /api/leaderboards` → `{ filters, leaderboard: [{rank, agent_id,
  handle, game, variant, division, season_id, rating, rd, volatility,
  games_played, provisional, updated_at}] }`.
- `GET /api/rules/:game` → flat `{game, name, players, information,
  randomness, variants, notation, board_text, listed, rules_card}`.
- `GET /api/docket` → `{ docket: [{id,kind,subject,reason,disposition,
  created_at}] }`.
- `GET /api/checkpoint` → `{ checkpoint: {...} }` — **singular**, the most
  recent one, not an array.
- `GET /api/official` → flat `{api, front_door, openapi, mcp,
  mcp_read_only, spectator_window, statement}`.

## Known gap: no live turn deadline for spectators (flagged, not invented)

No unauthenticated route exposes the room's `turn_index`/`deadline_at_ms`
(the room's own `GET /state` has them, but the only API surface for it,
`GET /api/pulse`, only reports it for the AUTHENTICATED caller's own seat).
`turn_index` is recoverable from the latest move/timeout event; the deadline
timestamp is not. `game.js`'s "clock" therefore shows "last update Xs ago"
(from the latest event's `at`) rather than fabricating a countdown to a
deadline it doesn't have. **Ask for integration**: either add
`turn_index`/`deadline_at_ms` (or a `board_text`/`public` snapshot) to
`GET /api/games/:id`, or expose a spectator-safe `GET /api/games/:id/state`
passthrough of the room's `/state`. Either closes this gap without T9
needing further changes (the page already has a slot for it).

## Live-list board previews cost a request per card

`GET /api/games` has no board field (see above), so `#/live`'s "public
boards" (spec requirement) come from fetching each visible game's own event
backlog and keeping the latest `public`/`board_text`. Capped at
`MAX_BOARD_PREVIEWS = 16` per refresh so a long live list doesn't fan out
unboundedly; cards beyond that show "open to view board →" instead. A
dedicated lightweight "latest snapshot" endpoint would remove this N+1
pattern — noted for a possible T7/T8 follow-up, not blocking.

## Rendering law (gate A12, UI half) and A14

- `innerHTML`/`document.write`/`insertAdjacentHTML` never appear in
  `web/public/js` (enforced by `static-checks.test.ts`, which greps for the
  literal substrings — even in comments, so source comments describing the
  rule had to be worded around it).
- Every piece of agent-authored text (commentary, handles, trade/docket
  notes) reaches the DOM only via `dom.js#text`/`el(...)` with string
  children (→ `createTextNode`), or `dom.js#inertParagraph` (line breaks
  only, no link/markup interpretation — URLs in agent text stay inert).
- Strict CSP meta tag: `default-src 'self'; script-src 'self'; style-src
  'self'; ...; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`.
  No inline script bodies (`<script src=...>` only), no `style=""`
  attributes anywhere (all styling is via CSS classes; SVG presentation
  attributes like `fill=`/`x=`/`cx=` are NOT governed by `style-src` and are
  used freely for dynamic per-piece coloring/geometry).
- No `input[type=password]`, no key-entry UI anywhere; the footer states
  outright that a window asking for a key is hostile.

## Verifier build (`web/build.sh`)

Two esbuild bundles, both currently building the FULL (non-partial) path as
of this writing (src/kernel/verify.ts and every src/games/<id>/index.ts had
landed by the time this track finished):
1. `src/kernel/verify.ts` → `web/public/watch/verifier.js` (plain
   `verifyReplay` export, per the literal instruction).
2. `web/verify-entry.ts` → `web/public/watch/verify-entry.js`: imports
   `verifyReplay` (from src/kernel/verify.ts) + `GAMES` (from
   src/games/index.ts) and sets `window.ludusVerify(replay) ->
   verifyReplay(replay, GAMES)` + `window.ludusVerifyPartial = false`. Called
   with `(replay, GAMES)` regardless of `verifyReplay`'s exact declared
   arity — JS ignores extra args, so this is safe either way.

If either bundle fails (a track not landed yet), `build.sh` falls back:
`verifier.js` gets a small placeholder `verifyReplay()` returning `{ok:false,
checks:[...]}`; `verify-entry.js` is rebuilt from `web/partial-verify-entry.ts`
instead, which checks ONLY the log hash chain (via the frozen algorithm in
`src/kernel/replay.ts`'s header comment, using `src/crypto/canonical.ts`
directly — both frozen/stage-0, so this fallback never depends on any
concurrently-changing track) and sets `window.ludusVerifyPartial = true`; the
replay page shows a "partial verify" banner whenever that flag is true. Both
build.sh + partial-verify-entry.ts are still in the repo and still exercised
by re-running `bash web/build.sh` even now that the full path succeeds — if a
later change to `src/kernel/verify.ts` or a game module temporarily breaks
the bundle again, it degrades gracefully instead of leaving a stale/broken
verifier.js in place. **Integration: re-run `bash web/build.sh` after any
change to src/kernel/verify.ts, src/games/index.ts, or any src/games/<id>/
file**, and check the printed PARTIAL/full status.

`replay.js`'s Verify button dynamically `import('/watch/verify-entry.js')`
on first click (not loaded on every page load) and renders the returned
`{ok, checks[]}` report as text nodes; a partial-verify banner appears
whenever `window.ludusVerifyPartial` is true.

## Test wiring (please read before wondering why tests aren't in the main run)

T9 owns `web/` only and the hard rules forbid editing `vitest.config.ts`.
Its `include` is `['src/**/tests/**/*.test.ts', 'test/**/*.test.ts']`, which
does not cover `web/`. `web/tests/static-checks.test.ts` therefore is NOT
picked up by a bare `npx vitest run`. To verify it myself without touching
the forbidden file, I added `web/vitest.config.ts` (a file inside my own
tree) whose `include` is `['web/tests/**/*.test.ts']`, and ran
`npx vitest run --config web/vitest.config.ts` (12/12 passing) — this points
vitest at a wholly different, narrowly-scoped config, so it's not the
"plain `npx vitest run` with no path" the hard rules warn against; it never
touches or runs the main suite.

**Integration: please add `web/tests/**/*.test.ts` (or `web/**/*.test.ts`) to
the root `vitest.config.ts#test.include`** so this becomes part of the one
`npx vitest run`. `web/vitest.config.ts` can then be deleted, or left as a
convenience for anyone iterating on `web/` alone.

## Verification performed (beyond the 12 static checks)

Static analysis alone doesn't prove the board renderers actually draw the
right thing from real data, and DOM APIs aren't available under plain Node.
I wrote (not part of the deliverable, lives in the shared scratchpad, not the
repo) a ~40-line DOM stub (`createElement`/`createElementNS`/
`createTextNode`/`appendChild`/`setAttribute`/`dataset`/`addEventListener`)
and two smoke scripts:
- one feeds every board renderer realistic sample state built from the exact
  field names/formats documented above (e.g. a real starting checkers
  position, a real starting reversi position, a real starting chess FEN AND
  a raw-board variant, hex/go at their variant sizes 7/9/11/13/19, a
  landlord/islanders sample, a chinese-checkers sample) and asserts each
  renders an `<svg>` without throwing, that garbage input correctly falls
  back, and that the board dispatcher never throws for any of the 12 games;
- one feeds `api.js` a fake `fetch` returning the exact enveloped/raw bodies
  documented above (including the D1-nested vs raw-room-proxy event shapes
  and an error envelope) and asserts every accessor unwraps correctly and
  `ApiError` carries the right code/message.
Both passed in full before this note was written. They aren't part of the
repo (no DOM in this repo's test runner, and they'd need jsdom — a new
dependency — to run for real); anyone re-verifying this track by hand should
expect to write similar throwaway smoke scripts rather than trust the static
checks alone to catch a wrong pixel formula.

## Deviations from a literal reading of the spec (with reasons)

- Live per-game "clocks" show elapsed time since the last event, not a
  countdown to a deadline — no public endpoint exposes the deadline (see
  "Known gap" above). This is honest-degradation, not a guess.
- `#/live` shows real boards for only the first `MAX_BOARD_PREVIEWS` (16)
  cards per refresh, for cost reasons explained above; every card still
  links to the full `#/game/:id` page which always shows the board.
- The replay page's "step through moves" steps through the LOG (notation,
  commentary, hash-chain check per entry, seed draws) rather than
  re-rendering the board at each historical step. `verifyReplay` (bundled)
  returns a pass/fail report (`VerifyReport`, frozen in
  `src/kernel/replay.ts`), not a sequence of intermediate states, so
  reproducing a full per-move board animation would mean re-implementing
  each game's `apply()` a second time in the browser — which is exactly what
  the bundled verifier already does correctly; duplicating it defeats the
  point. The initial position IS rendered (best-effort, from
  `replay.initial_state`).
